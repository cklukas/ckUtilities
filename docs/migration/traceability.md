# ckVision migration traceability ledger

This is the living WP-0 record linking each legacy product area to a
framework-neutral acceptance suite and its migration work package. It records
what users must be able to do, not how Turbo Vision implemented it.

## Application inventory

|---|---|---|---|---|

It selects separate built-in-default and personal-binding schemes; selecting defaults leaves personal bindings intact and the next edit reactivates the personal scheme. One suite catalog drives both each executable's declared title/category/default chord and Config's command-only registries, so app-specific bindings are edited and stored under the target app while shared `ckv.*` bindings remain global; target executables reload both at startup. The framework-independent Markdown core now toggles bold/italic/strikethrough/delimiter-safe inline-code selection and heading 1–6 markers while protecting code; the controller restores Unicode selections through the validated ckVision API. The live view displays the latest 160 messages only, with a retention notice, while complete history remains available to export and the response service; first response output is immediate and later small chunks are coalesced through ckVision's checked active-block replacement with incremental realized-tail reflow. | CKU-RELEASE | packaging | build, test, install, package, and run every executable | WP-10 | installed-product gate rebuilds the suite, stages a disposable prefix, and runs `--help` for every native executable. `CKTOOLS_CKVISION_CUTOVER=ON` now composes only ckVision products and framework-neutral cores under the production binary names, without configuring or installing the legacy UI runtime; `verify_ckvision_cutover` rejects legacy linkage, installed artifacts, and installed public-header references. Upstream candidate acceptance, permanent legacy removal, and the full release matrix remain |

Every row will gain links to domain tests, deterministic headless scenarios,
interactive platform tests, and release evidence before its work package can
close.

## Initial ckVision gap ledger

| Gap ID | Neutral requirement | First validating slice | State |
|---|---|---|---|
| CV-GAP-001 | A result controller needs to reveal and select a stable node without synthesizing input. Large changing hierarchies need provider-backed incremental refresh without duplicating their domain tree. | CKU-JSON, CKU-DU | `TreeView::reveal_and_select` and stable-ID `TreeModel` are in clean candidate `9f097ecde219a35971ccde6f8732b07ef021c35b`; TreeView owns expansion/selection and queries only visible paths. JSON and disk usage consume it directly, and a one-million-root test proves five painted rows issue five item queries. Application-scale refresh and memory acceptance remain |
| CV-GAP-002 | A long streaming rich-text document may need active-block updates, bottom anchoring, selection/copy, and bounded relayout. | CKU-CHAT | checked `FlowView::replace_block` with incremental realized-tail reflow implemented in ckVision candidate `bf4c1c6`; ckUtilities bounds the live transcript and coalesces small response updates. Viewport anchoring and selection/copy require an independently specified generic need |
| CV-GAP-003 | Runtime keymap editing needs a focused control that captures a normalized chord without allowing that chord to dispatch as a command. | CV-GAP-004 | The initial color-selection workflow uses ckVision's existing declarative radio-form dialog; bounded application diagnostics use its injected diagnostics observer. | CV-GAP-007 | A controller that commits a semantic document transformation needs to restore a current selection without private editor access or stale-revision cursor mutation. | CKU-EDIT | `TextEditor::set_selection` is in clean candidate `9f097ecde219a35971ccde6f8732b07ef021c35b`; it validates current revision, document positions, and grapheme alignment before moving the selection. ck-edit uses it after one Markdown transaction, with direct ckVision and adopting-application normal/ASan/UBSan coverage |
